## 3. 项目概述

### 3.1 项目背景

#### **3.1.1 业务现状与痛点**

当前教培业务过程中存在以下痛点：

1.  **售前咨询人力成本高、响应不及时，潜在学员流失**
    教培行业售前咨询量大、重复性问题多（课程方向、价格、报名流程、是否包就业等），人工客服难以
    7×24 小时覆盖，夜间/高峰时段响应慢，游客和潜在学员容易流失。

2.  **用户意向模糊、课程体系复杂，难以精准匹配课程**
    学员常以“想学编程”这类模糊表达咨询，而平台课程分类树庞大、方向与岗位对应关系复杂，人工匹配效率低且不专业，容易出现推荐偏差或过度营销。

3.  **学员学习路径不清晰、缺乏个性化规划，学习效率低**
    购课后学员面对大量课程不知道“先学什么、后学什么”，零基础与有基础学员需求差异大，缺乏结合岗位目标和前置依赖的个性化路径，导致学习混乱、完课率低。

4.  **课后答疑依赖人工、响应慢，且答案难以溯源到课件**
    学员学习中的问题量大且碎片化，授课老师无法即时响应；普通问答工具回答缺乏依据、无法定位到原始课件位置，学员难以对照学习，未解决问题也缺乏转交机制。

5.  **学员学习过程缺乏监督，异常掉队无人干预**
    在线学习自律性差，学员长时间不学习、进度停滞时平台难以及时发现和触达，续费与完课转化受损；单独建设触达通道成本高。

综上，需要建设智能体平台，用 Agent
把教培行业“售前获客—课程匹配—学习规划—课后答疑—过程督学”五个环节中依赖人工、响应慢、不精准、难溯源的痛点，转化为可自动化、可追溯、可个性化的
AI 服务链路。

#### 3.1.2 业务背景

-   课程体系为**编程课**，课件以 PDF
    形式存在（大章节一文档），每个章节对应多个教学视频（MP4）。
-   视频按课件讲解，但非逐字照读，存在口语解释与自由发挥。
-   学生按视频学习，需要边学边练；教师/教研需要出题、组卷、批改与学情分析。
-   平台同时服务销售、教学、教务等多类业务场景。

### 3.2 项目定位

**码帮智 ·
教育智能体平台**是面向编程课教育场景的多智能体系统，基于领域驱动设计（DDD）的限界上下文思想划分业务领域，每个业务领域由独立的智能体（Agent）承载，共享基础设施层通过
Ports & Adapters 实现依赖倒置。

系统主要用于：

-   信息查询（课程咨询、答疑）；
-   辅助决策（课程推荐、学习路径规划、学情分析）；
-   自动处理（出题、判分、督学触达）；
-   提升业务效率（7×24 服务、降低人工成本、主动流失预警）。

系统不用于：

-   替代人工决策；
-   执行业务审批；
-   承担专业责任（不编造课程与答案）。

## 4. 项目目标

### 4.1 总体目标

建设一个能够覆盖“售前获客—课程匹配—学习规划—课后答疑—过程督学—自主练习—学情分析”全链路、由多智能体承载、以确定性规则兜底
LLM 输出的智能化教育平台。

### 4.2 具体目标

|      |                                                         |
|------|---------------------------------------------------------|
| 编号 | 目标                                                    |
| G-01 | 支持游客/潜在学员完成 7×24 小时在线课程咨询与线索留资   |
| G-02 | 提供精准的课程推荐与个性化学习路径规划能力              |
| G-03 | 提供基于课件/视频的答疑与知识点溯源能力                 |
| G-04 | 提供按视频粒度的自主练习、自动出题与自动批改能力        |
| G-05 | 提供学习过程监督与异常督学、流失预警能力                |
| G-06 | 提供学情分析能力（长期画像、掌握度趋势、薄弱点归因）    |
| G-07 | 降低售前咨询人力成本，提升响应及时性与线索转化率        |
| G-08 | 以确定性规则兜底 LLM 输出，保证出题、判分、统计的可靠性 |

### 4.3 设计目标

-   业务领域独立建模，上下文之间通过端口与事件交互，不共享业务模型。
-   共享基础设施层仅承载纯技术能力，避免成为耦合中心。
-   每个上下文可由一个智能体或一组协作子智能体承载，支持独立演进。
-   出题、批改等场景中 LLM 输出不可靠时，以确定性规则兜底。

## 6. 系统范围

### 6.1 系统包含范围

系统支持以下业务上下文（各由一个智能体承载）：

|            |                |                                                           |            |
|------------|----------------|-----------------------------------------------------------|------------|
| **上下文** | **智能体**     | **职责**                                                  | **优先级** |
| 智能营销   | 营销 Agent     | 内容投放、线索获取、转化话术                              | 高         |
| 智能助教   | 助教 Agent     | 答疑、引导式教学、日常互动                                | 高         |
| 智能出题   | 出题 Agent     | 组卷、按知识点/视频出题、课件结构化                       | 高         |
| 智能评价   | 评价 Agent     | 自动批改、Rubric\[**评分量规**\] 评分、考试诊断、评价报告 | 高         |
| 学情分析   | 学情分析 Agent | 长期学习画像、掌握度趋势、薄弱点归因                      | 高         |
| 自主练习   | 自主练习 Agent | 练习会话管理、按视频触发出题、合并多视频题目              | 高         |
| 智能课程   | 课程 Agent     | 课程推荐、学习路径规划                                    | 低         |

### 6.2 系统不包含范围

当前版本不包含：

-   家校沟通、教研题库运营等第二梯队 Agent；
-   按负载拆分微服务（初期为模块化单体）；
-   独立考试评价上下文（视变更节奏待定）。

后续作为独立需求评估。

### 6.3 上下文关系

                 营销 Agent          助教 Agent  
                         \               /
                          \             /
                —— 共享基础设施层（LLM/记忆/可观测性/工具注册）——
                          /      |      \
                 出题 Agent —— 自主练习 Agent —— 批改 Agent —— 学情分析 Agent

-   上下文之间通过端口 + 领域事件交互，禁止直接依赖彼此领域模型。
-   学情分析为下游消费者，通过端口订阅练习、批改、答疑等事件，不反向依赖。
-   自主练习是编排者：调用出题 Agent 生成题目，调用批改 Agent
    批改，结果回流学情分析。

### 6.4 上下文判定原则

新业务是否独立成上下文，看三点：**业务语言是否不同、规则约束是否不同、变更节奏与消费者是否不同**。仅功能不同而规则同源的，应作为已有上下文的子模块。

### 6.5 架构约束

#### 6.5.1 分层结构

    ai-assistant-platform/
    ├── shared/                          # 跨上下文共享，严格限定纯技术
    │   ├── common/                      # 零依赖工具
    │   │   ├── util/                    # StringUtil, JsonUtil, DateUtil
    │   │   └── exception/
    │   └── infrastructure/              # 技术能力
    │       ├── llm/                     # LLM 客户端封装
    │       ├── memory/                  # 会话记忆存储
    │       ├── observability/           # 日志、追踪、token 统计
    │       └── tool-registry/           # 工具注册基础设施
    ├── contexts/                        # 按业务领域隔离
    │   ├── sales_assistant/
    │   ├── teaching_assistant/
    │   ├── course_assistant/            # 可以后面做
    │   ├── exam_paper_generation/       # 出题
    │   ├── self_practice/               # 自主练习
    │   ├── exam_grading/                # 批改
    │   └── learning_analytics/          # 学情分析
    └── orchestrator/                    # 意图路由层，不承载业务逻辑（预留，本次交付不实现）

#### 6.5.2 依赖规则

-   依赖方向严格单向：contexts/\* → shared/infrastructure →
    shared/common。
-   context 之间禁止互相依赖，跨上下文通过端口 + ACL 交互。
-   shared/common 零外部依赖；shared/infrastructure
    可依赖技术栈，不得依赖任何 context。
-   用 ArchUnit 或模块依赖检查守住上述规则。

#### 6.5.3 共享基础设施准入标准

放入 shared
的东西必须同时满足：**无业务语义、真实多方使用、接口稳定**。带业务语义的共用物（如用户信息查询、金额计算规则）不得放
shared，应通过端口/ACL/Shared Kernel/独立上下文处理。

#### 6.5.4 部署形态

初期采用**模块化单体**：单进程内按上述目录组织，通过接口隔离。某个上下文（如营销）负载或团队规模需要独立部署时再拆微服务。

## 7. 用户使用场景

### 7.1 场景名称：售前课程咨询

#### 7.1.1 场景描述

用户希望：以“想学编程”等模糊表达了解课程方向、价格、报名流程，并获得匹配的课程推荐。

#### 7.1.2 输入

用户输入：咨询文本（可能模糊，如“想学编程”）。

#### 7.1.3 系统处理

系统：

1.  分析输入，判断咨询意图（分类引导 / 课程介绍 / 报名就业 /
    学习咨询）；
2.  多轮对话引导用户逐级选择课程分类（一级分类 → 二级分类）；
3.  选定二级分类后，实时调用已有课程系统接口查询该分类下课程；
4.  经大模型组织生成推荐话术；
5.  咨询中记录留资并挂接 VIP 报到流程。

#### 7.1.4 输出

返回：识别出的一级/二级分类、课程推荐（课程名、时长、封面、简介）、答复内容、留资记录结果。

### 7.2 场景名称：学习路径规划

#### 7.2.1 场景描述

用户希望：购课后获得结合岗位目标与前置依赖的个性化学习计划。

#### 7.2.2 输入

用户输入：岗位方向（Java 开发岗 / 大模型算法岗 /
大模型应用开发岗）、学员基础信息（学历/专业）。

#### 7.2.3 系统处理

系统：

1.  询问学员岗位方向与基础信息；
2.  基于“岗位→课程路径”知识库查询对应课程；
3.  遵循课程前置依赖生成学习顺序与内容；
4.  结合学员基础调整（零基础补基础、有基础跳过）；
5.  绑定真实课程/章节 ID，进度变化时动态重规划。

#### 7.2.4 输出

返回：个性化学习计划（课程清单、学习顺序、学习内容），支持直接跳转学习。

### 7.3 场景名称：课后答疑

#### 7.3.1 场景描述

用户希望：学习过程中获得即时答疑，并能定位答案对应的原始课件位置。

#### 7.3.2 输入

用户输入：学习问题。

#### 7.3.3 系统处理

系统：

1.  基于课程视频/课件进行 RAG 检索；
2.  讲解知识点并溯源定位到原始课件位置；
3.  未解决问题按教师-学生分配关系转授课老师。

#### 7.3.4 输出

返回：知识点讲解 + 课件定位；未解决时转人工。

### 7.4 场景名称：自主练习

#### 7.4.1 场景描述

用户希望：按已学视频发起练习，巩固知识，并自动获得判分与反馈。

#### 7.4.2 输入

用户输入：勾选一个或多个已学完的视频。

#### 7.4.3 系统处理

系统：

1.  展示该章节下已学完的视频列表（含时长、标题）；
2.  校验累计时长 ≥ 60 分钟（&lt;30 分钟硬拦截，30–60 分钟软提示，≥60
    分钟放行）；
3.  生成
    practiceId，按视频并行出题（有题复用打乱，无题按锚点截取出题）；
4.  合并多视频题目为一套题，按视频分组展示；
5.  学生作答后选择题自动判分，主观题调批改 Agent，回填作答记录。

#### 7.4.4 输出

返回：一套按视频分组的题目及本次练习结果（对错、参考答案、解析、批改反馈、汇总）。

### 7.5 场景名称：智能督学

#### 7.5.1 场景描述

用户希望：学习异常（长时间不学习、进度停滞）时被及时提醒。

#### 7.5.2 输入

用户输入：学习行为数据（时长、进度）。

#### 7.5.3 系统处理

系统：监测学习时长与进度，异常时复用现有短信/微信通道自动触达提醒。

#### 7.5.4 输出

返回：提醒通知。

## 8. 功能需求

### 8.1 智能客服模块（咨询助手 Agent）

面向游客与潜在学员，7×24 在线提供课程咨询与线索收集。

#### 8.1.1 FR-001 课程分类引导

-   **功能描述**：客服 Agent 通过多轮对话引导用户选择课程分类：先选一级分类（人工智能 / 前端开发 / 后端开发 / 数据库开发），再选该一级分类下的二级分类；用户不确定时可引导直接找老师咨询。
-   **输入**：咨询文本（可能模糊，如”想学编程”）。
-   **输出**：识别出的一级分类与二级分类。
-   **业务规则**：分类树来自已有课程系统接口（getAllSubject），实时获取并缓存；对模糊意向主动追问澄清；多轮对话中记住已选择的一级/二级分类。

#### 8.1.2 FR-002 课程介绍咨询

-   **功能描述**：用户选定二级分类后，实时调用已有课程系统接口（getFrontCourseList，携带二级分类 id 与一级分类 id）查询课程列表，经大模型组织生成课程推荐话术。
-   **输入**：一级分类、二级分类。
-   **输出**：课程推荐（课程名、时长、封面、简介）。
-   **业务规则**：课程列表实时查询；无匹配课程时如实告知（不编造），并引导留资；话术只介绍课程名称与核心内容，不展示课时与价格，不假设用户学习路径。

#### 8.1.3 FR-003 报名与就业咨询

-   **功能描述**：回答报名/入学流程、是否包就业等咨询。
-   **输入**：咨询问题。
-   **输出**：答复内容。

#### 8.1.4 FR-004 学习咨询

-   **功能描述**：回答学习类常见问题（如是否可自学、学习周期等）。
-   **输入**：咨询问题。
-   **输出**：答复内容。

#### 8.1.5 FR-005 线索留资与跟进

-   **功能描述**：咨询过程中记录用户留资（电话/微信/意向方向），形成线索并支持后续跟进。
-   **输入**：联系方式、意向方向、备注。
-   **输出**：留资记录结果。
-   **业务规则**：留资可挂接现有 VIP 报到流程。

### 8.2 个性化学习与智能助教模块

面向已购课学员与 VIP 学员，提供学习路径规划、答疑与督学。

#### 8.2.1 FR-006 学习路径规划

-   **功能描述**：询问学员岗位方向（Java 开发岗 / 大模型算法岗 /
    大模型应用开发岗），查询对应课程，经大模型生成个性化学习计划（学习顺序 +
    学习内容）。
-   **输入**：岗位方向、学员基础信息。
-   **输出**：个性化学习计划（课程清单、学习顺序、学习内容）。
-   **业务规则**：基于岗位→课程路径知识库生成；遵循课程前置依赖（先学 A
    再学 B）；结合学员基础（学历/专业）调整，零基础补基础、有基础跳过。

#### 8.2.2 FR-007 学习计划落地与调整

-   **功能描述**：学习计划绑定真实课程/章节
    ID，学员可直接跳转学习；学习进度变化时动态重新规划。
-   **输入**：学习进度数据。
-   **输出**：更新后的学习计划。

#### 8.2.3 FR-008 答疑助教

-   **功能描述**：基于课程视频/课件进行知识问答，讲解知识点并溯源定位到原始课件位置；未解决的问题转授课老师。
-   **输入**：学习问题。
-   **输出**：知识点讲解 + 课件定位。
-   **业务规则**：基于课程视频/课件 RAG
    检索回答；未解决问题转授课老师（联动教师-学生分配关系）。

#### 8.2.4 FR-009 智能督学

-   **功能描述**：监测学员学习时长与进度，异常时通过短信/微信触达提醒。
-   **输入**：学习行为数据（时长、进度）。
-   **输出**：提醒通知。
-   **业务规则**：复用现有短信/微信通道触达。

### 8.3 自主练习模块

#### 8.3.1 背景与目标

学生在按视频学习过程中进行自主练习，巩固知识。练习按**视频粒度**发起，而非学完整个章节。出题内容来源于课件，通过锚点截取保证权威性与上下文可控。练习结果持久化，支撑批改与学情分析闭环。

#### 8.3.2 FR-010 已学视频展示与多选

仅展示学生已学完的视频，展示标题与时长，支持多选。

#### 8.3.3 FR-011 时长准入校验

选中视频累计时长 ≥ 60 分钟才允许出题；&lt;30 分钟硬拦截，30–60
分钟软提示，≥60 分钟放行。

#### 8.3.4 FR-012 锚点截取出题

从 Chapter.contentMd 用 find(startSentence) 与 find(endSentence)
截取区间；失败用 fallbackRange 兜底；超 2000 字按段落二次切分或先摘要。

#### 8.3.5 FR-013 题型定义

固定题型：选择题、简答题、场景分析题必出；代码题按区间内是否有 \`\`\`
代码块自动判断，无则静默跳过。

#### 8.3.6 FR-014 题量映射

题量按视频时长区间映射：&lt;5 分钟 3–5 道；5–15 分钟 5–8 道；15–30 分钟
8–12 道；&gt;30 分钟 10–15 道（封顶 15）。

#### 8.3.7 FR-015 题型分配

有代码块时代码题约占 30%（上限 4 道），其余按选择:简答:场景 ≈ 4:3:2
分配。

#### 8.3.8 FR-016 多视频合并题量控制

多视频合并时设总题量上限 30 道，超出按比例缩减，每视频保底 3 道。

#### 8.3.9 FR-017 题目复用

同一 videoId 首次生成后复用，打乱顺序；提供“换一批”重新生成。

#### 8.3.10 FR-018 练习归属

一次练习共用一个 practiceId，题目按 videoId 归属并挂到该 practiceId。

#### 8.3.11 FR-019 自动判分与批改

选择题自动判分；主观题与代码题调批改 Agent 回填
isCorrect、score、feedback。

#### 8.3.12 FR-020 结果展示

按视频分组展示一套题，提交后展示对错、参考答案、解析、批改反馈与本次汇总。

#### 8.3.13 出题 Prompt 约束

-   **选择题**：4 选项、1 正确、干扰项基于常见误区、输出 JSON。
-   **简答题**：考察概念理解，参考答案要点 3–5 条，输出 JSON。
-   **场景分析题**：构造含角色/目标/约束的具体场景，给出参考解题思路，输出
    JSON。
-   **代码题**：只考察代码逻辑理解，代码过长时引用关键片段，输出 JSON。
-   概念类题型 prompt 注明“忽略代码块，只基于文字讲解出题”。

#### 8.3.14 锚点标注规范

-   首句选“内容起点句”，跳过过渡语；尾句选“内容结束句”，跳过收尾语。
-   首句尽量选带独特信息（知识点名称、公式、代码标识）的句子，避免
    Markdown 中多次出现。
-   匹配不上时在 fallbackRange 填写章节范围（如 2.1\~2.3）兜底。
-   先标一个章节的 10 个视频跑通闭环，验证后再批量标。

### 8.4 智能体设计

#### 8.4.1 通用设计原则

-   一个上下文对应一个主 Agent，内部可按任务拆子 Agent，由主 Agent
    调度。
-   Agent 之间用结构化 schema（如 JSON
    Schema）契约通信，不用自然语言交接。
-   Agent
    只做自然语言入口与解释；核心计算（题量、判分、统计）用确定性代码。
-   每个 Agent 的工具按上下文隔离，不建全局工具大杂烩。

#### 8.4.2 各 Agent 职责摘要

|                |                              |                                  |
|----------------|------------------------------|----------------------------------|
| Agent          | 核心能力                     | 确定性/LLM 分工                  |
| 营销 Agent     | 内容生成、话术、线索跟进     | LLM 生成，规则约束投放           |
| 助教 Agent     | 答疑、引导式教学             | LLM 为主，知识库检索辅助         |
| 课程 Agent     | 推荐、路径规划               | 规则 + LLM 解释                  |
| 出题 Agent     | 按视频/知识点出题、组卷      | 截取与题量确定性，题目生成用 LLM |
| 自主练习 Agent | 会话管理、准入校验、合并题目 | 流程确定性，入口用 LLM           |
| 批改 Agent     | 逐题批改、反馈               | rubric 确定性校验 + LLM 评分解释 |
| 学情分析 Agent | 画像、趋势、归因             | 统计确定性，归因解释用 LLM       |

## 9. 业务规则

### 9.1 核心业务规则

#### 9.1.1 智能客服规则

-   对模糊意向主动追问澄清；课程分类需引导到二级分类（一级 → 二级）。
-   课程分类树与课程列表来自已有课程系统接口，实时查询（分类树缓存）。
-   无匹配课程时如实告知（不编造），并引导留资。
-   多轮对话中记住已选择的一级/二级分类；留资挂接 VIP 报到流程。

#### 9.1.2 学习路径规划规则

-   基于岗位→课程路径知识库生成学习计划。
-   遵循课程前置依赖（先学 A 再学 B）。
-   结合学员基础（学历/专业）调整，零基础补基础、有基础跳过。
-   计划绑定真实课程/章节 ID，进度变化时动态重规划。

#### 9.1.3 答疑规则

-   基于课程视频/课件 RAG 检索回答。
-   未解决问题转授课老师（联动教师-学生分配关系）。

#### 9.1.4 自主练习规则

-   仅展示已学完视频，累计时长 ≥ 60 分钟才允许出题（&lt;30 硬拦截，30–60
    软提示，≥60 放行）。
-   题量按视频时长区间映射（封顶 15）；多视频合并总题量上限
    30，超出按比例缩减，每视频保底 3 道。
-   有代码块时代码题约占 30%（上限 4 道），其余按选择:简答:场景 ≈ 4:3:2
    分配。
-   同一 videoId 首次生成后复用，打乱顺序，支持“换一批”。
-   选择题自动判分；主观题与代码题调批改 Agent。
-   出题截取、题量计算、判分统计用确定性代码；LLM 只做生成与解释。

### 9.2 默认处理规则

当用户输入信息不足：

系统应该：

-   请求补充信息（多轮追问澄清方向与基础）；
-   返回默认结果；
-   给出提示。

### 9.3 数据不足规则

当系统无法获得有效信息：

系统：

-   不允许编造结果（无匹配课程、无课件依据时如实告知）；
-   明确提示信息不足；
-   必要时建议人工处理（转授课老师、转人工）。

## 10. 系统处理流程

### 10.1 普通业务流程

    用户提交请求
         ↓
    系统理解请求
         ↓
    判断业务类型
         ↓
    获取相关数据
         ↓
    处理业务逻辑
         ↓
    生成结果
         ↓
    返回用户

### 10.2 自主练习主流程

    学生进入自主练习
      → 展示该章节下已学完的视频列表（含时长、标题）
      → 学生勾选一个或多个视频
      → 校验：选中视频累计时长 ≥ 60 分钟？
           否 → 提示已选时长与差额，不允许开始
           是 → 生成 practiceId
      → 对每个选中视频并行：
           查该 videoId 已有题目？
             有 → 复用，打乱顺序
             无 → 按锚点截取 → 计算题量 → 调模型出题 → 入库
      → 合并所有题目为一套题，按视频分组展示
      → 学生逐题作答并提交
      → 选择题自动判分；主观题调批改 Agent
      → 回填 PracticeAnswer，返回本次练习结果

### 10.3 前置流程：课件与视频准备（离线）

1.  课件 PDF 批量转 Markdown，存入 Chapter.contentMd（保留标题 \#
    与代码块 \`\`\`）。
2.  视频上传时 ffprobe 获取 durationSeconds，写入视频元数据。
3.  教研人工标注每个视频的锚点（startSentence、endSentence），存为
    VideoAnnotation。
4.  学生观看视频，完成记录写入 StudentVideoProgress。

## 11. 异常处理需求

### 11.1 外部服务异常

当：第三方服务（LLM 服务等）不可用。

系统：

-   尝试备用方案（重试一次）；
-   返回降级结果；
-   提示用户。

### 11.2 数据查询失败

系统：

-   尝试其他来源（fallbackRange 兜底）；
-   无结果时明确说明（不编造，提示人工复核）。

### 11.3 系统异常

要求：

-   隐藏内部错误；
-   返回用户可理解提示。

### 11.4 异常场景处理清单

|                      |                                                    |
|----------------------|----------------------------------------------------|
| 场景                 | 处理                                               |
| 锚点匹配失败         | 用 fallbackRange 兜底；仍失败提示人工复核          |
| 截取区间超长         | 按段落二次切分或先摘要                             |
| 选中视频无代码块     | 静默跳过代码题，不提示                             |
| 某视频出题失败       | 其他视频正常返回，失败视频提示重试或从其他视频补题 |
| 累计时长不足 60 分钟 | 拦截并提示已选时长与差额                           |
| 学生未学完视频       | 不出现在可选列表                                   |
| LLM 输出不符合 JSON  | 重试一次，仍失败则该题丢弃并记录日志               |
| 批改异常             | 标记异常转人工，不阻塞其他题                       |

## 12. 安全需求

### 12.1 数据安全

系统必须：

-   防止非法修改；
-   防止数据泄露。

### 12.2 权限控制

|               |                                |
|---------------|--------------------------------|
| 角色          | 权限                           |
| 游客/潜在学员 | 使用售前咨询功能               |
| 学员/VIP 学员 | 使用学习、答疑、练习功能       |
| 教师/教研     | 出题、批改、学情分析、锚点标注 |
| 管理人员      | 管理系统                       |
| 维护人员      | 维护系统                       |

### 12.3 敏感信息保护

禁止暴露：

-   密钥；
-   Token；
-   内部配置；
-   系统日志。

## 13. 非功能需求

### 13.1 性能需求

系统应：

-   支持多视频并行出题；
-   单视频超时不影响其他视频；
-   保证响应速度；
-   避免重复计算（题目复用避免重复调用模型）。

### 13.2 可用性需求

系统：

-   单点故障不能导致整体不可用；
-   支持异常恢复（批改异常不阻塞其他题、单视频失败不影响整体）。

### 13.3 可维护性需求

系统支持：

-   功能扩展；
-   模块升级；
-   数据更新；
-   题型 prompt 与题量映射规则可配置，不硬编码。

### 13.4 可扩展性需求

未来支持：

-   新业务（第二梯队 Agent）；
-   新数据；
-   新接口；
-   按负载与团队规模拆分微服务。

### 13.5 易用性需求

要求：

-   操作简单；
-   无需学习复杂规则；
-   输出易理解；
-   代码题自动判断（而非用户选择）降低交互复杂度。

### 13.6 其他非功能约束

-   **成本**：题目复用避免重复调用模型；代码题仅在存在代码块时生成。
-   **可追溯**：题目保留 videoId 与来源 practiceId，支持溯源与质量排查。
-   **数据一致性**：出题成功后批量插入题目；提交后批量插入作答。
-   **架构约束**：context 间禁止直接依赖，shared 不依赖 context，用
    ArchUnit 守住。

## 16. 业务边界

明确：

系统可以：

-   提供课程信息查询与 7×24 在线咨询；
-   辅助决策（课程推荐、学习路径规划、学情归因）；
-   自动处理（按视频出题、自动判分、督学触达）；
-   提升业务效率。

系统不能：

-   编造课程与答案（无依据时如实告知/建议人工）；
-   替代人工决策；
-   执行业务审批；
-   承担专业责任。

## 附录 B. 关键设计决策记录

1.  **限界上下文划分 Agent
    边界**：每个业务领域独立上下文，共享基础设施仅放纯技术能力。
2.  **按视频出题而非按章节**：解决整章上下文过长、注意力稀释问题。
3.  **锚点截取而非内容快照**：数据不冗余，标注轻量，依赖“视频按课件讲”的前提。
4.  **PDF 转 Markdown 存储**：保留标题与代码块结构，find 截取逻辑不变。
5.  **代码题自动判断而非用户选择**：降低交互复杂度，编程课场景保留代码题价值。
6.  **题目按 videoId
    复用**：自主练习场景提升性能与学情可比性，不引入题库复杂度。
7.  **多视频合并为一套题**：前端体验统一，后台按 videoId
    分组支撑批改与学情定位。
8.  **确定性代码兜底 LLM**：出题截取、题量计算、判分统计用代码；LLM
    只做生成与解释。
9.  **模块化单体起步**：不提前拆微服务，按负载与团队规模演进。
